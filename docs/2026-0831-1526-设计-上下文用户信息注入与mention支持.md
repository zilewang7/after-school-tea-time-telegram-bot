# 上下文用户信息注入与 mention 支持设计

## 设计目标（用户视角）

群友让 bot "@一下张三" 或 bot 主动想点名某人时，bot 能真正打出可点击的提及：有 username 的用户输出 `@zhangsan`，没有的输出 `[张三](tg://user?id=123)`（渲染成 text_link 提及）。做到这点靠在系统提示词里附上"当前上下文中出现过的用户"名册——名字、user id、username——而聊天上下文正文维持现状（`#N 用户名:` 仍然只用 first name，不加噪音）。

## 现状与前提调研

- **库里没有 username**：messages 表只有 `userId` + `userName`（first name）；`ctx.from.username` 从未落库。要给出 `@handle` 必须新增用户资料存储。
- **mention 的两种形态**（入库侧 telegram-md-entities 已处理）：
  - `text_mention`（无 username 用户被点名）→ 存储文本里已是 `[名字](tg://user?id=123)`，自带 id；
  - 纯文本 `@username` → 原样存文本，不带 id，要名册反查。
- **出库侧已支持**：md→entities 渲染器对 `tg:` scheme 链接放行并产出 `text_link` 实体（link-target.ts 明确允许 `tg:`），所以 LLM 写 `[名字](tg://user?id=…)` 即可成为可点击提及；`@username` 更是纯文本天然可用。
- **messages 表也没有 userId 列**（实现时发现，设计初稿写错了）：`saveMessage` 收 userId 只用来算 fromBotSelf。已补列（INTEGER nullable，sqlite 方言无 BIGINT、其 INTEGER 本就 64 位），新消息开始记录，老消息作者条目退化为"名字 + id 未知"，随时间自愈；`saveMessage` 里对 `Number(env)` 可能产生的 NaN 做了清洗（写 null）。
- `ContextMessage` 目前不带 `userId`（只有 userName），需要补投影。

## 方案

### 1. 新表 `telegram_users`（用户资料登记簿）

`telegramUserDTO.ts`：`userId`(PK) / `username`(nullable) / `firstName` / `lastName`(nullable) / `updatedAt`。`timestamps: false`，自维护 updatedAt。

**采集点（autoSave，全部 upsert、幂等）**：
- 每条消息的 `ctx.from`（作者，最主要来源）；
- `forward_origin.type === 'user'` 的 `sender_user`（被转发者）；
- `entities` 里 `text_mention` 的 `user`（被点名的无 username 用户）。

变化才写（比较后 skip），不给热路径加写放大。**存量数据没有**：老消息作者的 username 要等 TA 再冒泡一次才知道，名册里显示为"未知"，随时间自愈。

### 2. 上下文名册收集（新文件 `src/reply/context-users.ts`）

`collectContextUsers(contextMessages)`，在 buildContext 组装完 contextMessages 后调用：

- **作者**：非 bot 消息的 `userId`（ContextMessage 补 `userId` 字段）；
- **被提及者**：扫描各消息 text 中的 `tg://user?id=(\d+)` 和 `@[A-Za-z0-9_]{4,32}`；
- **bot 分组**（补遗二，2026-08-31 深夜）：`telegram_users` 补 `isBot` 列（harvest 从 `User.is_bot` 写入，老行 null 自愈），名册条目带 `isBot`；提示词里 bot 单独列在"以下是 bot 账号（不是人，@ 它们没有任何作用，不要提及）"块中，避免模型去 @ bot。mention 指引同时改为**优先 `[名字](tg://user?id=数字)`**（名字用 first name），拿不到 id 才退 @username；
- **被转发原作者**（补遗，2026-08-31 晚）：messages 再补 `forwardFromId` 列（`forward_origin.type === 'user'` 时写原发送者 id；隐私保护转发无 id，维持只有名字字符串），名册按"仅被提及"收录——此前资料虽被 harvest 进 telegram_users，但消息行只存显示字符串，链路断在无 id 可查；
- 统一去 `telegram_users` 查资料（id 批量 IN + username 批量 IN，各一条查询）；
- 产出 `ContextUser[]`：`{ userId?, username?, firstName, mentionedOnly }`。查不到任何补充信息的 `@handle`（无 id 无资料）不收录——名册只列能给 LLM 增量信息的条目。bot 自己不收录。

### 3. buildContext 返回形态变更

`buildContext` 返回 `{ messages: UnifiedMessage[], contextUsers: ContextUser[] }`（原来裸返回 messages 数组）。调用点全量更新：chat-handler、retry-handler、offline 测试（约 6 处），类型检查兜底。

### 4. 提示词注入（动态层新段，条件注入）

`buildSystemPrompt(model, extras?: { contextUsers?: ContextUser[] })`，有名册时在"# 当前环境"后追加：

```
# 上下文中的用户

- 张三：id 123456789，@zhangsan
- 李四：id 987654，无 username
- 王五：id 未知，@wangwu（仅被提及）

需要提及（@）某人时：有 username 的直接写 @username；没有 username 的写
[名字](tg://user?id=数字)，会渲染成可点击的提及。你本来就在回复最后一条消息，
无需再 @ 它的作者；也不要 @ 与话题无关的人。
```

（评审新增：明确"无需重复 @ 你正在回复的用户"。）

- mention 用法说明跟名册绑定（无名册时整段消失，不污染上下文）；
- 聊天正文格式**不动**，仍是 `#N 用户名`（first name）。

### 5. 不改的

- 消息头渲染、编号、`[system]` 段落；
- messages 表结构（userId 已有列，只是补投影）。

## 风险与取舍

- **名册可能引导模型滥用 @**：提示词里明确"不确定就不要 @"；正文格式不变也降低了模仿风险。
- `@handle` 大小写：Telegram username 不区分大小写，查询用 LOWER() 归一。
- 误报：正文里的 `user@example.com` 这类不会命中（`@` 前面有字符时不算 mention）——正则用词边界处理；`@` 后 4-32 位字符是 Telegram 规则。
- upsert 热路径开销：每消息一次比较+可能一次写，SQLite 单行 upsert 可忽略；失败静默降级（名册少条目而已）。
