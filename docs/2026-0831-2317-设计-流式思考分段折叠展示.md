# 流式思考（CoT）分段折叠展示设计

## 设计目标（用户视角）

模型思考得越久，现在消息里那段引用块就越长，聊天窗口被半成品的推理刷屏、正文被挤到视野外。改成"滚动预览"：思考过程始终只有最近两段以明文引用块可见，更早的段落随流式实时收进可展开的折叠引用块里；思考一结束（正文开始输出或流结束），全部思考收进折叠块——和现在定稿后的样子一致。整个过程消息高度基本恒定，想回看完整推理点开折叠块即可。

## 现状

- `formatStateForDisplay`（response-handler.ts）流式阶段把整段 `thinkingBuffer` 放进**非折叠** blockquote（`wrapInBlockquote(…, expandable = !isProcessing)`），定稿/续接定稿/错误展示才收成 expandable。
- Telegram 客户端每次 editMessageText 后 expandable blockquote 默认回到收起态——这正是"边流式边折叠"可行的前提。
- 超长思考已有两道闸：`THINKING_BUFFER_LIMIT = 10000` 整体截断、消息预算超限拆续接消息（续接拆分用 `renderThinkingForStreaming` 精确测量，测量函数必须与展示函数同源）。

## 方案

### 1. 分段器 `segmentThinking(raw: string): string[]`

新文件 `src/telegram/formatters/thinking-display.ts`：

- **主规则（Gemini 形态）**：按空行（`\n{2,}`）切段——Gemini CoT 天然是带小标题的多段落。
- **兜底规则（其它 platform，段落不明显）**：任何一段超过 `SEGMENT_SOFT_LIMIT ≈ 400 字符`（约合 Gemini 一段的典型占用，中英文按字符近似即可）时继续细分，切点优先级：段内最后一个换行 → 最后一个句末标点（`。！？.!?` 后跟空白）→ 超过 `SEGMENT_HARD_LIMIT ≈ 600` 时按词边界硬切。DeepSeek/Anthropic 等即便整段无空行也能被切成大小接近 Gemini 段落的伪段落。
- 最后一段永远视为"未完成"（还在流入），参与计数但内容不回填合并。

### 2. 流式渲染 `formatThinkingForStreaming(raw, { answerStarted })`

设 `n = 段数`：

| 状态 | 展示 |
|---|---|
| 思考进行中，`n ≤ 3` | 全部段落 → 一个**非折叠** blockquote（现状不变，起步零跳动） |
| 思考进行中，`n > 3` | 段 `1…n-2` 合并 → **expandable** blockquote（编辑后默认收起）；段 `n-1、n`（最近两段）→ 非折叠 blockquote 供预览 |
| 思考结束（`textBuffer` 非空 或 流 done） | 整段 → expandable blockquote（与现有定稿一致） |

两个引用块之间以单个 `\n` 相接（两个独立 blockquote 实体，Telegram 支持相邻不合并）。折叠头内部段落间保留 `\n\n`。markdown 仍按 `streaming: true` 渲染。

### 3. 接线点

| 文件 | 改动 |
|---|---|
| `src/telegram/formatters/thinking-display.ts`（新） | `segmentThinking` + `formatThinkingForStreaming` |
| `src/reply/response-handler.ts` | `formatStateForDisplay` 的 thinking 分支改调新函数（`answerStarted = Boolean(state.textBuffer)`）；续接拆分的 `renderThinkingForStreaming` 测量函数**同步改用新函数**（测量与展示必须同一路径，否则长度/实体数对不上） |
| 定稿路径 | `final-message-builder.ts`、`error-display.ts`、`finalizeCurrentMessage` 不动——它们已经是"全收起" |

### 4. 不改的

- 落库内容（存的还是原始 thinking 文本，展示层切段不影响持久化与下一轮上下文）；
- `THINKING_BUFFER_LIMIT` 截断、续接消息机制、状态行轮播；
- 定稿后的最终形态（一个 expandable 引用块）。

## 补遗（评审后修正，2026-08-31 深夜）

"段"的定义修正为**节 = 标题 + 其下段落内容**（Gemini CoT 的 `**小标题**` + 若干段落），而非每个空行段落单独计数。实现改为两级：先按空行切段落单元（超 400/600 的兜底细分不变），再聚合成节——单元首行是标题行（`#{1,6} ` 或整行 `**…**`）即开新节，无标题的单元贪心并入当前节、以 ~900 字符为节上限（近似 Gemini 一节的占用，兜底覆盖无标题的 platform）。折叠/预览计数以节为单位；贪心聚合不前瞻，前缀稳定性保持。

## 风险与取舍

- **实体预算**：流式期思考从 1 个 blockquote 实体变 2 个，加上内部 markdown 实体，仍远低于 85 上限；测量函数同源保证拆分判断准确。
- **收起是客户端行为**：依赖"每次编辑后 expandable 默认收起"，这与现有定稿折叠是同一机制，已被长期验证。
- **段落边界抖动**：最后一段还在流入时，其内容一旦越过 soft limit 会被兜底切分，视觉上等价于"新起一段"，可接受；已进折叠头的段落不再变动（分段是纯函数、前缀稳定）。
- **正文开始后思考立即全收起**：比现状更早收起（现状要等定稿），正是需求本意；Gemini 偶发的"正文后再思考"交错场景极罕见，收进折叠块继续追加即可，不特殊处理。

## 验证

1. `tsc --noEmit`；offline 新用例：分段器（空行切段 / 无空行长文本兜底切分 / 混合）、渲染状态机（≤3 段全明文、>3 段头收尾露二、answerStarted 全收）、前缀稳定性（同一 raw 追加内容后，已折叠段落切分不变）。
2. test 实例实测：挑长思考 prompt（gemini thinking 模型）观察流式期消息高度是否恒定、折叠块可展开、定稿形态不变；再用 deepseek/anthropic 验证兜底分段。
