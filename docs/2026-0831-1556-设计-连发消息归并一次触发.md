# 连发消息归并一次触发设计

## 设计目标（用户视角）

用户在私聊里一次转发多条消息（或短时间内连发几条触发消息）时，bot 不再每条各回一次、每条只看到孤立的上下文，而是等这一串发完后**只回复一次**，且这一次回复能看到整串消息。典型场景：转发 5 条群聊记录 + 补一句"帮我总结下"，bot 只在最后一条下回一条完整的总结。

## 现状

- 触发链路：`registerChatHandler` 的 detached handler → `willReply`（私聊恒真；群里看 @/回复 bot/命令）→ `tryMarkUserMessageHandling` 幂等占位 → `handleReply`。
- 每条触发消息独立走完整流程：转发 5 条 → 5 次触发、5 个 placeholder、5 条回复；且转发消息互相之间没有 reply 关系，每次 buildContext 只看到那一条自己。
- 上下文树 = reply 链（`replyToId` 反查）+ `message_links`（/chat 拉入的旁观消息，insert-only、幂等、随小时清理过期）。**归并可以完全复用 `message_links`**：把先到的批内消息挂到锚点消息上，buildContext / 媒体等待 / 编号 / retry 全部自动生效，无需新表。

## 方案

### 1. 归并窗口（新文件 `src/reply/mention-batcher.ts`，纯内存）

批次 key：`chatId:userId`。触发消息（`willReply` 为真、**非命令**）到达时：

- **已有开窗批次** → 并入（记录 messageId、更新锚点 ctx 为本条）：
  - 本条是**纯文字消息**（非转发、无媒体）→ **立即归并触发**。打字消息通常是"转发完了，这是我的问题"，立即触发把常见场景的额外延迟压到 0；
  - 本条是转发/媒体消息 → 重置窗口计时，继续等。
- **无开窗批次**：
  - 本条是**转发消息**（`forward_origin` 存在）或**带媒体的消息**（有无 caption 均算）→ 开窗等待。转发/媒体才有"后面还有"的信号；媒体消息开窗还有一个副作用收益：500ms 正好盖过极小媒体的下载耗时，消掉"⏳ 正在获取媒体"通知秒删的闪现（见 §3）；
  - 纯文字消息 → **立即触发，行为与今天完全一致**（不给日常对话加延迟）。

窗口参数：滑动窗口 **500ms**（批量转发到达间隔实测在 500ms 内；每条并入重置）；硬上限 10s（从开窗算起，防止无限顺延）；批次成员上限 20 条（到达即触发）。窗口时长读 `MENTION_BATCH_WINDOW_MS`（默认 500），offline 测试注入短窗口用。

### 2. 归并触发（flush）

- 锚点 = 批内**最后一条**消息（bot 的 placeholder / 回复都挂在它下面，与"名册"提示词里"你正在回复最后一条"的语义一致）。
- flush 时先 `saveMessageLinks(chatId, 锚点, 先到的成员们)`，再 `handleReply(锚点 ctx, { mention: true })`。
- 之后一切走现有机制：`getRepliesHistory` 从锚点出发经 links 收齐整批（含各成员的媒体、media group 子图）；`awaitMediaWithFeedback` 覆盖批内所有媒体；`#N` 编号按时间序排列；**retry / 版本切换重建上下文时 links 在库里，整批依然在**。

### 3. 顺带修复：媒体通知闪现

现状：`awaitMediaWithFeedback` 只要媒体还在下载就立刻发"⏳ 正在获取消息中的媒体"，极小媒体几百毫秒就下完 → 通知刚发出就被删掉，闪一下。

修复：发通知前先静默轮询一个 **500ms 宽限期**，期间下载完成就直接返回（不发通知）；超过宽限期仍未完成才发通知。总等待预算不变。叠加批次窗口的 500ms，小媒体场景通知彻底消失；大媒体照旧有反馈。

### 4. 幂等与边界

- 每条消息**到达并入时**就 `tryMarkUserMessageHandling` 占位（防 Telegram 重投递把同一条塞进两个批次）；flush 不再占位。
- media group 子消息沿用现有 `shouldSkipMessage` 判定，在**入批前**跳过（一个相册 = 一个成员）。
- 命令（/pic /vid /picbanana /picgpt /chat）不进批、不受批影响，立即独立处理（现状不变）。
- 不同用户互不影响（key 含 userId）；群里同用户短时连 @ 两次也会归并成一次回复。
- 进程重启丢内存批次 → 这批消息不会被回复（与今天"处理中重启丢消息"同级别，可接受）。

### 5. 不改的

- 消息落库（autoSave）、上下文渲染格式、`[forwarded from …]` 标注、提示词。
- 单条普通打字消息的路径与延迟（零变化）。

## 风险与取舍

- **孤立转发/媒体单条会多等 ~500ms**：无法预知后面没有了。500ms 感知上可忽略，还换来通知不闪现。
- **打字消息立即 flush 的误伤**：用户转发中途插一句话会提前触发，后续转发成为新批次、再触发一次。取舍：常见场景（转发完→提问）零延迟收益更大。
- **锚点 ctx 持有**：内存里持 grammy Context 数秒，无泄漏风险（flush/超限即释放）。
- links 表复用 /chat 的清理与幂等语义，无 schema 变更。

## 验证

1. `tsc --noEmit` + offline 全量（含新用例，注入 200ms 窗口）。
2. test 实例：私聊一次转发多条 → 一条回复且引用完整内容；转发后补一句话 → 立即回复；群里连续两条 @ → 一次回复。
